# Research: Platform toggle for the watcher pipeline

## Research Question
Add a required `platforms: { linkedin, threads }` boolean block to `watcher.config.json` that switches each acquisition leg on or off independently — a disabled platform never fetches, never judges, and never appears in the digest or heartbeat; both false is a clean logged no-op (exit 0, no email, no state write); a missing or malformed block fails the run naming the file and key.

## Summary

The change is small and lands in two modules plus three consumers. `src/config-file.ts` owns validation through a closed `ALLOWED_KEYS` set (`src/config-file.ts:44`) and one `read<Key>(value, key, filePath)` validator per key; the new key must join both the set and the `WatcherConfig` interface or every currently valid file fails at the unknown-key check (`src/config-file.ts:91-95`). `src/index.ts` already partitions the raw config into a LinkedIn arm and a Threads arm (`src/index.ts:189-194`) and already guards each arm on a non-empty partition, so filtering the partitions by the flags is sufficient to skip a platform end-to-end — no new gate machinery is needed.

Three consequences the FRD does not state and the code forces: (1) a REQUIRED key is new to this codebase — every existing validator is either required-reject (`readStringArray`, `src/config-file.ts:108`) or optional-with-default (`readScrollRounds`, `src/config-file.ts:208`), and the absent-means-error decision needs the reject shape at three levels (block, member, type); (2) two non-watch consumers run the same validator — the PC tick (`scripts/fetch-linkedin.ts:237`) and the probe job (`scripts/probe-judge.ts:50`) — so the required key reaches them the moment the code lands, which makes same-commit discipline (code + committed config) load-bearing; (3) the both-off no-op cannot sit before the `LLM_ACCOUNTS` resolve without either skipping the secret check or moving that resolve above the fetch stage for every run.

## Detailed Findings

### Config validation — `src/config-file.ts`

- `WatcherConfig` (interface, immediately above `ALLOWED_KEYS` at `src/config-file.ts:44`) carries six fields; `platforms` becomes the seventh and the only nested-object member.
- `ALLOWED_KEYS` (`src/config-file.ts:44-51`) is a closed `as const` tuple. The unknown-key loop in `validateConfig` (`src/config-file.ts:84-95`) rejects any key outside it with `config: <path> has unknown key \"<key>\" — allowed keys: ...`. Adding `platforms` to the tuple is mandatory, not optional.
- Validator call sites are one line each inside `validateConfig` (`src/config-file.ts:98-105`): `readStringArray`, `readSurfaces`, `readRecencyHours`, `readReasoningEffort`, `readScrollRounds`. `readPlatforms` joins this list and its result joins the returned object.
- Two validator templates exist and neither fits alone: `readStringArray` (`src/config-file.ts:108`) is the required-reject shape (absent `undefined` fails the `Array.isArray` test); `readScrollRounds` (`src/config-file.ts:208`) is the optional-with-default shape (`value === undefined -> DEFAULT_SCROLL_ROUNDS`). The chosen absent-means-error contract uses the reject shape at three levels: the block itself, each member, and each member's type.
- House error form is `config: <filePath> \"<key>\" <rule>` — every message carries the path and the offending key. `readScrollRounds` also demonstrates the reject-don't-floor rule for values that are present but wrong (`src/config-file.ts:208-220`).
- `resolveSurfaces` (`src/config-file.ts:227`) throws when a `linkedin` surface reaches it — the PC leg consumes those raw. The toggle must not change this: filtering the Threads partition still has to exclude `type === \"linkedin\"` entries, or a linkedin-only config with threads off would leak a linkedin surface into the resolver and fail the run.

### Funnel wiring — `src/index.ts`

- The raw partition already exists (`src/index.ts:189-194`): `linkedinSurfaces` filters `type === \"linkedin\"`; `surfaces` resolves everything else. Both arms are already empty-guarded — the Threads walk runs only when `surfaces.length > 0` after `resolveSession` (`src/index.ts:203-217`), and the payload arm only when `linkedinSurfaces.length > 0` (`src/index.ts:220`). Intersecting each partition with its flag reuses both guards; no new skip branch is required.
- `resolveSession(env)` runs unconditionally at the top of the acquisition stage (`src/index.ts:203`) and `cleanupSessionDir` pairs it in the `finally` (`src/index.ts:245`). FRD #4 (no session resolve when threads is off) is satisfied only if the Threads partition is empty — the resolve itself still runs on a linkedin-only tick. This is acceptable: the session dir is created and removed, no network call happens.
- The health resolve is hoisted above Gate 1 (`src/index.ts:271-282`) with a recorded trade: a malformed `LLM_ACCOUNTS` exits 1 even on a nothing-unseen tick. `resolveJudgeConfig` throws; `loadAccountHealth` degrades silently. The both-off no-op must sit AFTER this pair to keep the secret check (developer decision, below).
- Gate 1 (`src/index.ts:302-312`) fires the heartbeat on every zero-unseen tick — the 144-emails-a-day stream the discover rationale cited. The both-off no-op returns before `HeartbeatStats` construction (`src/index.ts:284`) and before `loadState` (`src/index.ts:299`), so no email is built and the state file is never read.
- The `timing: fetch` line (`src/index.ts:248`) and the extract count line (`src/index.ts:251`) both print on every run that reaches the acquisition stage. With the surfaces log keeping full config truth (developer decision, below), the extract count line's `config.surfaces.length` stays truthful as \"surfaces configured\".

### Rendering — heartbeat and digest

- The LinkedIn leg line attaches to `HeartbeatStats` only when the payload reader ran this tick (`src/index.ts:284-297`). `linkedinLegLine` (`src/heartbeat.ts`) renders only when the field is present, and `buildDigest` (`src/email.ts`) renders the leg line only when the status is not `ok`. Consequence: `platforms.linkedin: false` silently drops the leg line from both emails — which FRD #3 endorses. No render change is needed.
- The startup surfaces log (`src/index.ts:184`) maps over `config.surfaces` — the RAW list, linkedin entries included (the D14 comment above it explains why). With the toggle, this line keeps listing everything configured and a new `watch: platforms: ...` line goes above it (developer decision, below).
- `buildSubject` (`src/email.ts`) appends the ` + LinkedIn` suffix only when at least one match is non-threads. A threads-only run stays byte-identical to the pre-LinkedIn subject; a linkedin-only run gets the suffix. No change needed.

### Non-watch consumers of the validator

- `scripts/fetch-linkedin.ts:237` resolves `deps.config ?? loadWatcherConfig()`, then partitions linkedin surfaces (`scripts/fetch-linkedin.ts:238-244`) and no-ops when the partition is empty. The PC tick validates the ENTIRE config, so the new required key reaches it. Per the discover decision the PC leg never honors the flags — its only obligation is to keep validating and keep fetching.
- `scripts/probe-judge.ts:50` loads the config once at module scope for the keyword list. Same exposure: a stale clone running new code against an old config fails the probe with the platforms error.
- Migration hazard with no precedent in this repo: both prior config-shape changes added OPTIONAL keys, so a stale clone never broke. A required key inverts that — any clone (PC loop, probe runner) that pulls code without pulling `watcher.config.json` fails until it syncs. Same-commit discipline covers a clean pull; a dirty PC clone does not.

### Test surface

- `tests/config-file.test.ts` builds every case from a `VALID` literal (`tests/config-file.test.ts:8-13`) that has no `platforms`. A required key makes nearly every existing case throw the platforms error FIRST, so `VALID` must gain the block before any other assertion is meaningful. New cases: missing block, missing member, non-boolean member (string and number), both-off accepted, each single-off accepted.
- The committed-file happy path (`tests/config-file.test.ts`, \"loads the committed config file\") reads the real `watcher.config.json` — it fails until the committed file ships the block. `watcher.config.json` is 141 lines, 3-space indented, `recencyHours` last (`watcher.config.json:141`); the block lands before it.
- `tests/index.test.ts` injects config through `WatcherDeps.config` and already stages payload doubles: mixed run (`tests/index.test.ts:479`), absent payload (`:532`), belt fault (`:595`), stale (`:641`). New funnel cases mirror them: linkedin-only with a staged payload, threads-only with a `linkedinFetch` double asserting ZERO calls, both-off asserting zero fetch calls, no email, and an ENOENT state oracle.

## Architecture Insights

- **The partition IS the gate.** Both arms are already empty-guarded, so the toggle needs no new branch inside the acquisition stage — filtering the two arrays at `src/index.ts:189-194` is the whole wiring. This is the smallest change that satisfies \"never fetches, never judges, never emails\".
- **A required key is a new validator class here.** Every existing key is either required-reject or optional-with-default; `platforms` is the first key whose absence is an error AND whose shape is a nested object with two required members. The validator therefore has three rejection levels (block, member, type) and is the first multi-level validator in the module.
- **The both-off no-op is a placement problem, not a behavior problem.** \"Exit 0, no email, no state write\" is easy; placing the return so it still honors the secret check (developer decision) is what forces the design fork in Open Questions.
- **Rendering needs no change.** The leg line is already conditional on the reader having run, and the subject suffix is already conditional on a non-threads match existing. A disabled platform disappears from both emails for free.
- **Migration risk is inverted from precedent.** Optional keys never broke a stale clone; a required key does. The PC loop's dedicated clone of main is the exposure, and it is the one clone that pulls on its own schedule.

### Composite Lessons

- Config-shape changes in this repo have never needed a follow-up fix — the validator + closed-set + committed-file discipline is the load-bearing pattern (`68c1e2d`, `d8fc15b`).
- Both precedents shipped the committed `watcher.config.json` change in the same commit as the code; with a required key that discipline stops being hygiene and becomes correctness (`68c1e2d`).
- The PC leg's dedicated clone of main is the only consumer that pulls on its own schedule — it is the migration exposure a required key creates (`scripts/fetch-linkedin.ts:237`).

## Developer Context

**Q (discover: Config home): Where should the platform on/off switch live?**
A: `watcher.config.json` key — committed, hand-editable, one knob per platform; repo doctrine puts operator-tuned values in committed data.

**Q (discover: Gate point): Where should the toggle gate the pipeline?**
A: Filter the existing partitions in `runWatcher` — smallest change, no new machinery; a disabled platform never fetches, judges, or emails.

**Q (discover: Absent-key behavior): What should a run do while the setting is still missing from the file?**
A: Errors until you add it — fail-visible contract; a missing required key exits non-zero naming the problem, never silently defaults.

**Q (discover: Truth table): Which table is the rule for the four flag combinations?**
A: Independent flags — each flag controls its own platform only.

**Q (discover: Setting shape): How should the true/false setting be written in `watcher.config.json`?**
A: Grouped object (`platforms: { linkedin, threads }`) — one validator, one missing-error path, room for future per-platform knobs.

**Q (discover: Both-off behavior): When both members are false, what should each run do?**
A: Quiet no-op — a deliberate off is not an error; the alternative keeps the heartbeat firing 144 times a day at the 10-minute cron.

**Q (discover: PC fetch leg): `linkedin=false` — should the always-on PC loop keep fetching LinkedIn, or pause too?**
A: Hosted run only — LinkedIn stays warm, so re-enabling is a single boolean flip with data already pushed.

**Q (`src/index.ts:271-282`): Both flags off = the watcher is parked. If something else is also broken (a typo in the `LLM_ACCOUNTS` secret), should the parked run fail or exit quietly?**
A: Still check secrets — both-off still resolves `LLM_ACCOUNTS` first; a typo exits 1 naming `LLM_ACCOUNTS`, so a broken secret stays visible while parked. Consequence: the no-op return sits AFTER `resolveJudgeConfig`, which is below the fetch stage today — see Open Questions.

**Q (`src/index.ts:184`): At startup the watcher prints one line listing everything it watches. If you turn LinkedIn off, what should that startup log show?**
A: Add a status line — keep the full config list and print `watch: platforms: linkedin on, threads off` above it. The extract count line keeps counting `config.surfaces.length` (surfaces configured).

## Open Questions

- **Both-off return placement vs the secret check.** \"Still check secrets\" forces the no-op return to sit after `resolveJudgeConfig` (`src/index.ts:271`), but the fetch stage (`src/index.ts:196-246`) runs BEFORE that line today. Two placements: (a) return after the health resolve — the fetch stage still runs with two empty partitions, so `resolveSession` (`src/index.ts:203`) resolves and cleans a session dir for nothing and the `timing: fetch` line still prints; (b) hoist the no-op check above the fetch stage and move `resolveJudgeConfig` up with it — a malformed `LLM_ACCOUNTS` then exits 1 BEFORE any fetch on EVERY run, flipping the recorded trade at `src/index.ts:271-282` for all ticks, not just both-off ones. Design must pick one.
