# Solution Analysis: Platform toggle for the watcher pipeline

**Date**: 2026-11-08T17:37:32+0700
**Author**: Yogiswara Utama
**Commit**: 77f44d7
**Branch**: ukind/feature-toggle
**Repository**: feature-toggle

## Research Question
Add a required ``platforms: { linkedin, threads }`` boolean block to ``watcher.config.json`` that switches each acquisition leg on or off independently — a disabled platform never fetches, never judges, and never appears in the digest or heartbeat; both false is a clean logged no-op (exit 0, no email, no state write); a missing or malformed block fails the run naming the file and key.

## Summary
**Problem**: One operator knob per platform that gates the funnel end-to-end, with a required-key fail-visible contract and a both-off parked run that stays quiet.
**Recommended**: Partition filter — intersect the two existing surface arms with the flags and place the both-off return after the secret resolve. Zero ordering change for normal ticks.
**Effort**: Low (0.5–1 day: validator ~30 lines, funnel wiring ~10 lines, tests, config block)
**Confidence**: High

## Problem Statement

**Requirements:**
- Required ``platforms`` block with two boolean members; absent or malformed fails the run naming file and key.
- Each flag gates its own platform only: no fetch, no judge, no digest/heartbeat presence.
- Both off: exit 0, no email, no state write — but the secret check still runs (locked discover decision).
- The PC LinkedIn leg keeps fetching and validating (locked decision — hosted-run-only toggle).

**Constraints:**
- Closed ``ALLOWED_KEYS`` set must gain the key or every valid file fails the unknown-key check (`src/config-file.ts:91-95`).
- Same-commit discipline for code + ``watcher.config.json`` is correctness, not hygiene: a required key breaks any clone that pulls code without the config (`scripts/fetch-linkedin.ts:237`, `scripts/probe-judge.ts:50`).
- ``resolveSurfaces`` must never see a linkedin surface (`src/config-file.ts:229-233` throws).

**Success criteria:**
- A run with either flag false fetches only the enabled platform; both-email rendering stays correct with zero render changes.
- Both off: parked run exits 0 with log lines only — no email, no state read, no state write, secret typo still exits 1.
- ``npm run typecheck && npm run lint && npm test`` green.

## Solution Options

### Option 1: Partition filter
**How it works:**
Add ``readPlatforms`` to ``config-file.ts`` (three rejection levels: block, member, type) and intersect both arms with the flags at ``index.ts:189-194``. When both flags are false, return the Gate-1 shape after the health resolve (:282) — the secret check runs first (locked decision), the fetch stage has already run with two empty partitions and cost only a session-dir create/remove plus the timing/extract log lines.

**Pros:**
- Zero ordering change for normal ticks — the recorded trade at `src/index.ts:264-270` stays exactly as accepted.
- Both arms are already empty-guarded (`:209/:216/:220`), so the intersection is the entire funnel wiring.
- Rendering is free: a disabled platform never attaches ``linkedinLeg`` (`:293`) and never produces a non-threads match.

**Cons:**
- A parked tick still resolves+cleans a Threads session dir and prints `timing: fetch` + `extract: 0` lines. Cosmetic; "clean logged no-op" licenses logging, and no browser or network call happens (:203 materializes a storageState dir only).

**Complexity:** Low (~0.5–1 day)
- Files to create: 0
- Files to modify: 4 + tests (~40 src lines, ~150 test lines) + ``watcher.config.json``
- Risk level: Low

### Option 2: Early gate (hoisted secret check)
**How it works:**
Hoist ``resolveJudgeConfig`` (`:271`) above the fetch stage (`:196`) and return before any fetch when both flags are false. A parked tick touches nothing: no session dir, no timing line.

**Pros:**
- Strictest reading of "clean": a parked run performs zero fetch-stage side effects.

**Cons:**
- Flips the recorded, accepted trade (`:264-270`) for EVERY tick: malformed ``LLM_ACCOUNTS`` exits 1 before any fetch on all ~144 daily runs, not just parked ones — a global funnel reorder riding a per-platform toggle FRD.
- Reorders the degraded-accounts warn and rider construction relative to fetch logs on every run.

**Complexity:** Medium (~1 day + reorder re-verification)
- Files to modify: same as Option 1 + the hoist surgery + recorded-trade comment rewrite
- Risk level: Medium (documented-trade breakage)

### Option 3: Gate helper
**How it works:**
Extract a pure ``resolvePlatformPlan(config)`` returning the filtered arms + a ``parked`` predicate into ``config-file.ts``; the funnel consumes the plan. Truth-table logic lives in one unit-testable place. The placement fork (Option 1 vs 2) is still decided inside it — the helper does not resolve the open question.

**Pros:**
- The linkedin-exclusion hazard is contained in one pure function; 4-combination truth table tests in isolation.
- Pure-helper precedent is native to the repo (`src/recency.ts`, `src/linkedin-voyager.ts`).

**Cons:**
- A module-level exported unit for ~10 lines of boolean filtering — the smallest-change doctrine pays a packaging tax.
- Wins no dimension outright over Option 1; the funnel set must still be tested end-to-end anyway.

**Complexity:** Low-Medium (~1 day)
- Files to modify: Option 1’s set, restructured (+1 exported helper)
- Risk level: Low

## Recommendation

**Selected:** Option 1 — Partition filter

**Rationale:**
- The partition IS the gate: both arms are already empty-guarded (`src/index.ts:209/:216/:220`), so flag-intersecting the arrays at `:189-194` is the whole funnel wiring — the smallest change satisfying "never fetches, never judges, never emails".
- Zero ordering change: the recorded accepted trade at `src/index.ts:264-270` (malformed `LLM_ACCOUNTS` exit-1s even a Gate-1 tick) stays byte-identical in behavior and comment.
- The both-off return after the health resolve (:282) honors the locked discover decision — secret typo exits 1 while parked — with the Gate-1 return shape (`:310`): exit 0, no email, ``loadState`` (`:299`) and every persist path never reached.
- Validator discipline has precedent and zero follow-up history: `readStringArray` reject shape (`:108-128`) extended to three levels (block, member, type), rejecting never flooring per `readScrollRounds` (`:208-218`).

**Why not alternatives:**
- Option 2: blocked on integration-risk — it flips a documented, deliberately accepted trade for every tick to optimize a parked-only path. The FRD asks for a toggle, not a funnel reorder.
- Option 3: clears the filter but wins no dimension; its truth-table tests are worth taking as tests OF Option 1’s validator, not as a new module.

**Trade-offs:**
- Accepting a parked tick’s session-dir create/remove + two log lines for zero risk to normal-tick ordering.

**Implementation approach:**
1. `src/config-file.ts` — add ``platforms`` to ``ALLOWED_KEYS`` and the ``WatcherConfig`` type; write ``readPlatforms`` (missing block / missing member / non-boolean member each fail with path + key); wire into ``validateConfig`` (`:98-105`) and the return (`:105`).
2. `watcher.config.json` — add the block (both true) before ``recencyHours`` (`:141`), same commit as the code.
3. `src/index.ts:189-194` — intersect: linkedin arm also requires ``config.platforms.linkedin``; the non-linkedin filter keeps excluding ``type === "linkedin"`` (resolveSurfaces throw guard, `config-file.ts:229-233`).
4. `src/index.ts` — after the health resolve (:282), if both flags false: one ``watch: platforms off — parked`` log line + Gate-1-shaped return. Startup: add the ``watch: platforms: ...`` status line above the raw surfaces log (:184, D14 truth kept).
5. Tests — see Testing Strategy.

**Integration points:**
- ``src/config-file.ts:44-51`` — ALLOWED_KEYS + interface
- ``src/config-file.ts:98-105`` — validator wiring
- ``src/index.ts:189-194`` — flag intersection
- ``src/index.ts:282-284`` — parked return placement
- ``watcher.config.json:141`` — committed block

**Patterns to follow:**
- Required-reject validator with path + key in every message: `src/config-file.ts:108-128`
- Reject-don’t-floor for present-but-wrong values: `src/config-file.ts:208-218`
- Gate-1 return shape: `src/index.ts:310`

**Risks:**
- Stale-clone migration (required key): the PC loop clone and probe runner validate the whole file (`scripts/fetch-linkedin.ts:237`, `scripts/probe-judge.ts:50`) — ship code + config in one commit; a dirty PC clone fails visibly until synced, which is the fail-visible contract working.
- Linkedin-surface leak into ``resolveSurfaces`` if the threads-arm filter is rewritten carelessly: keep the ``type !== "linkedin"``` exclusion (`config-file.ts:229-233` catches it loudly, but the error would misreport operator intent as a wiring bug).

## Scope Boundaries
- Building: the ``platforms`` block, validator, funnel intersection, parked return, tests, committed config.
- NOT building: any env-var kill switch (`HEARTBEAT_ENABLED` stays separate by decision), PC-leg honoring of the flags, render changes in ``email.ts``/`heartbeat.ts` (none needed), workflow changes (file-based, no new secret).

## Testing Strategy

**Unit tests (tests/config-file.test.ts):**
- ``VALID`` literal (`:8-13`) gains the block first — otherwise every existing case throws the platforms error before its own assertion.
- Rejections: missing block, missing member (each of the two), non-boolean member (string and number), each naming path + key.
- Accepts: both-off, each single-off.
- Committed-file happy path stays green (requires the ``watcher.config.json`` block in the same commit).

**Funnel tests (tests/index.test.ts, mirroring the payload doubles at :479/:532/:595/:641):**
- linkedin-only (threads off) with a staged payload: linkedin posts flow, no Threads fetch.
- threads-only (linkedin off) with a ``linkedinFetch`` double asserting ZERO calls.
- both-off: zero fetch calls, ``transport.sendMail`` never called, state file ENOENT oracle (never read, never written), exit shape ``{judged: 0, matches: 0, skipped: 0, saved: false}```.
