# FRD: Platform toggle for the watcher pipeline

## Summary
Add a required `platforms: { linkedin, threads }` boolean block to `watcher.config.json` that switches each acquisition leg on or off independently. `runWatcher` filters the two existing fetch partitions before any fetch, so a disabled platform never fetches, never judges, and never appears in the digest or heartbeat. Both flags false is a clean logged no-op (exit 0, no email, no state write); a missing or malformed block fails the run naming the file and key.

## Problem & Intent
"i want to add feature toggle, there is linkedin and thread currently, add setting to wacher, if linkedin true, means only linkedin is run, if thread true, so linkedin and thread is run, if both false, then linkedin and thread is not run"

Stated motivation: **future flexibility** — no acute pain today. The developer wants the config knob in place so either surface can be switched off later without touching code.

## Goals
- One hand-editable setting in `watcher.config.json` that turns each platform on or off independently.
- A disabled platform costs nothing: no fetch, no LLM judge call, no email line.
- Flipping a boolean is the whole operation — no code change, no redeploy beyond the normal commit.

## Non-Goals
- Per-surface enable flags (e.g. disabling one Threads tag while keeping the rest) — the toggle is platform-wide.
- Pausing the PC-local LinkedIn fetch loop — the always-on PC leg keeps fetching and pushing regardless.
- Unifying this toggle with the existing `HEARTBEAT_ENABLED` env kill switch (`src/config.ts:33`) — different home, different lifetime.
- Any new pipeline stage, new surface type, or new env var.

## Functional Requirements
1. `watcher.config.json` SHALL accept a new top-level `platforms` object with two required boolean members, `linkedin` and `threads`.
2. A missing `platforms` key, a missing member, or a non-boolean member SHALL fail the run with an error naming the file path and the offending key. No silent default.
3. When `platforms.linkedin` is `false`, the run SHALL skip the LinkedIn payload read entirely — no `readPayloadPosts` call, no LinkedIn posts in the funnel, no LinkedIn leg line in the digest or heartbeat.
4. When `platforms.threads` is `false`, the run SHALL skip the Threads walk entirely — no session resolve, no `fetchSurfacesAuthenticated` / `fetchLoggedOutPosts` call, no Threads posts in the funnel.
5. When both members are `false`, the run SHALL log one line naming that no platforms are enabled, exit 0, send no email, and write no state file.
6. The PC-local LinkedIn fetch loop (`npm run fetch-linkedin` / `watch-linkedin`) SHALL be unaffected by the toggle — it keeps fetching and pushing `state/linkedin-posts.json` so LinkedIn stays warm.
7. The committed `watcher.config.json` SHALL be updated in the same change to include `platforms: { "linkedin": true, "threads": true }`, so the repo's own config satisfies the new required key.

## Non-Functional Requirements
- **Performance**: no specific constraint — the toggle only removes work from a run.
- **Security**: no new secrets. The setting is non-secret committed configuration, consistent with `keywords` / `surfaces` / `recencyHours`.
- **UX / Accessibility**: not applicable — CLI pipeline plus a hand-edited JSON file.
- **Reliability**: fail-visible on missing or malformed input (repo rule: no silent fallbacks); both-off is a deliberate no-op, not an error, and must not produce the 144-per-day heartbeat stream the 10-minute cron would otherwise generate.

## Constraints & Assumptions
- Node >= 22, strict TypeScript, ESM; the offline deterministic suite (`node:test` via `tsx`) is the only test surface.
- Config validation is a closed `ALLOWED_KEYS` set (`src/config-file.ts:44-51`) — the new key must be added there or every currently valid file fails.
- The toggle gates the hosted run only. The PC loop is a separate process on its own clone of main and does not read `watcher.config.json` for this purpose.
- Assumption: `platforms` absent means error (chosen over absent-means-on), so the committed config file must ship with the key in the same change.

## Acceptance Criteria
- [ ] `npm test` exits 0, with new cases covering: both on, linkedin only, threads only, both off, missing `platforms`, and a non-boolean member.
- [ ] Removing `platforms` from `watcher.config.json` makes a run exit non-zero with a message naming `watcher.config.json` and `platforms`.
- [ ] With `platforms: { "linkedin": true, "threads": false }` and a staged payload, the run judges LinkedIn posts only; with `{ "linkedin": false, "threads": true }` and staged surfaces, Threads posts only.
- [ ] With both false, the run logs one no-platforms line, exits 0, sends no email, and leaves `state/seen-posts.json` byte-identical.
- [ ] `npm run typecheck && npm run lint` exit 0.

## Recommended Approach
New required `platforms: { linkedin, threads }` key in `watcher.config.json`, validated by the closed `ALLOWED_KEYS` set in `src/config-file.ts` with a `readPlatforms(value, key, filePath)` validator that rejects bad values rather than flooring them. `runWatcher` filters the two existing partitions — `linkedinSurfaces` (`src/index.ts:220`) and the resolved `surfaces` array (`src/index.ts:209`) — before the acquisition stage, and both-off short-circuits to a logged no-op before Gate 1.

## Decisions

### Config home
**Question**: Where should the platform on/off switch live?
**Recommended**: `watcher.config.json` key
**Chosen**: `watcher.config.json` key
**Rationale**: committed, hand-edited, one knob per platform; repo doctrine puts operator-tuned values in committed data, and this one is meant to be flipped by hand. Evidence: closed `ALLOWED_KEYS` at `src/config-file.ts:44-51`.

### Gate point
**Question**: Where should the toggle gate the pipeline?
**Recommended**: Filter the existing partitions in `runWatcher`
**Chosen**: Filter the existing partitions in `runWatcher`
**Rationale**: smallest change, no new machinery; a disabled platform never fetches, judges, or emails. Evidence: `src/index.ts:209` (threads partition) and `src/index.ts:220` (linkedin partition).

### Absent-key behavior
**Question**: `watcher.config.json` has no true/false platform setting yet. What should a run do while that setting is still missing from the file?
**Recommended**: Runs as today (absent means both enabled)
**Chosen**: Errors until you add it
**Rationale**: fail-visible contract — a missing required key exits non-zero naming the problem, never silently defaults. Evidence: the config-error pattern at `src/config-file.ts:56-57`.

### Truth table
**Question**: Your sentences cover linkedin-only, both-on, and both-off — but `linkedin=false` + `threads=true` is unclear. Which table is the rule?
**Recommended**: Independent flags
**Chosen**: Independent flags
**Rationale**: each flag controls its own platform only, which satisfies all three sentences the developer stated.

### Setting shape
**Question**: How should the true/false setting be written in `watcher.config.json`?
**Recommended**: Grouped object (`platforms: { linkedin, threads }`)
**Chosen**: Grouped object
**Rationale**: one validator and one missing-error path, and the block leaves room for future per-platform knobs.

### Both-off behavior
**Question**: When both `linkedin` and `threads` are false, what should each run do?
**Recommended**: Quiet no-op
**Chosen**: Quiet no-op
**Rationale**: a deliberate off is not an error; the alternative keeps the heartbeat firing 144 times a day at the 10-minute cron.

### PC fetch leg
**Question**: `linkedin=false` — should the always-on PC loop keep fetching LinkedIn, or pause too?
**Recommended**: Hosted run only
**Chosen**: Hosted run only
**Rationale**: LinkedIn stays warm, so re-enabling is a single boolean flip with data already pushed.
